# الترحيلات — كيف تُرقّى نسخة مثبّتة دون إعادة تثبيت

## المشكلة التي حُلّت اليوم

الـ`Migrator` القديم كان ينشئ الجداول الناقصة فقط: `if (table exists) continue;`
— أي `ALTER` مستقبلي لم يكن ليصل إلى مشترٍ ثبّت نسخة قديمة، ولوحات الصدارة كانت
ستنفجر عنده بصمت. هذه كانت الفجوة رقم 1 في خطة المنتج.

## كيف يعمل الآن

1. **تثبيت جديد**: قاعدة فارغة → تنفيذ `db/schema.<driver>.sql` كاملاً → ختم
   `schema_version` بأعلى رقم في `db/migrations.json` (حالياً **5**).
2. **ترقية**: قاعدة فيها جداول → قراءة أعلى `version` → تنفيذ الخطوات الأحدث بالترتيب،
   وختم كل خطوة بعد نجاحها.
3. **تثبيتات ما قبل v3**: لا جدول `schema_version` لديها → تُقرأ كـ`0` → تمشي الملف
   كاملاً. (v1/v2 لم تُبع لأي مشترٍ، فلا يوجد مسار مكسور.)

## قواعد كتابة خطوة ترحيل

- خطوة واحدة لكل إصدار، بكلتا اللهجتين (`mysql` و`sqlite`) — المولّد لا يشطر عنك شيئاً هنا.
- كل عبارة **idempotent**: كرر التشغيل بعد انهيار في المنتصف يجب أن ينجح. الـMigrator يتسامح
  مع أخطاء «موجود مسبقاً» فقط: MySQL 1060/1061/1091، ورسائل SQLite المماثلة. أي خطأ آخر يوقف
  الترقية ويظهر للمشترٍ كما هو.
- البيانات القديمة تُعدَّل بـ`UPDATE` **داخل** الخطوة نفسها — لا تترك backfill للمشترٍ.
- عند إضافة عمود: عدّل `tools/bootstrap_schema.py` → أعد توليد الـSQL → ارفع
  `Migrator::CURRENT` → أضف الخطوة في `db/migrations.json` → شغّل `npm test`.

## مثال v3 (الذي أُضيف اليوم)

```
ALTER TABLE leaderboard ADD COLUMN period ...;      ADD COLUMN period_key ...;
UPDATE leaderboard SET period='week', period_key=week_key WHERE week_key <> '';
UPDATE leaderboard SET period='all',  period_key='all'   WHERE week_key = '';
DROP old unique/index;  CREATE new uniques/indexes (bucket-aware);
```

صفوفُ سجلٍّ قديمة بأسبوع فارغ تهبط في سلة `all` — قرار متعمّد: الأفضل أن تظهر في لوحة
«كل الأزمنة» بدل أن تختفي.

الفحص **D** يفعل الشيء نفسه لخطوتي v4 وv5: يبني الجداول الثلاثة بصيغتها المكسورة القديمة
**فعلاً**، يزرع فيها صفوفًا مكرّرة ويثبت أن القاعدة القديمة كانت تقبلها، ثم يطبّق الخطوتين
حرفياً من `db/migrations.json` ويتحقق من زوال التكرار، ومن رفض التكرار الجديد، ومن أن إعادة
التشغيل الثانية لا تغيّر عدد صفوف أي جدول.

## مثال v4 — حين يكون المولّد نفسه هو المعطوب

`PRIMARY KEY` كان يُصدر في فرع MySQL من `tools/gen_schema_sql.py` فقط. النتيجة: على SQLite
لم يكن لدى `settings` و`game_tag` و`collection_game` **أي** قيد تفرد — والـSQLite هو مسار
«التشغيل السريع بلا إعداد» الذي يجرّبه كل مشترٍ أولاً. الوسم نفسه يُلصق باللعبة مرتين،
ومفتاح الإعداد يُخزَّن مرتين، و`INSERT ... ON CONFLICT` ينفجر لأنه لا يجد قيداً يستهدفه.

إصلاح المولّد وحده لا يكفي: النسخ المثبّتة تبقى مكسورة. لذا خطوة v4 تُصلح القاعدة، بقاعدة
البيت نفسها — **البيانات القديمة تُعالَج داخل الخطوة**:

```
DELETE FROM game_tag WHERE rowid NOT IN (SELECT MIN(rowid) FROM game_tag GROUP BY game_id, tag_id);
CREATE UNIQUE INDEX IF NOT EXISTS uq_game_tag_game_id_tag_id ON game_tag (game_id, tag_id);
```

الـ`DELETE` قبل الـ`CREATE` ليس تزييناً: فهرس فريد على بيانات مكرّرة يُفشل الترقية في
منتصفها ويترك المشتري بلا موقع. وقائمة `mysql` في الخطوة **فارغة عمداً** — ذلك المخطط أعلن
هذه المفاتيح دائماً. الخطأ كان في مُصدِر SQLite وحده.

والدرس المُعمَّم في المولّد: `--verify` صار يقارن **مجموعات القيود** (pk/unique/index) بين
اللهجتين، لا ترتيب الأعمدة فقط. 77 قيداً متطابقاً الآن، وأي قيد يوجد في لهجة دون الأخرى
يفشل البناء.

## مثال v5 — سجل الترخيص

عمودا `audited_at`/`audit_verdict` على `game_licenses`، وجدول `license_audits` الجديد، وختم
`settings` بإصدار القواعد. عبارة `CREATE TABLE` داخل الخطوة منسوخة حرفياً من الملف المولَّد،
و`tools/verify_php.py` يقارن قائمة أعمدتها بالمخطط في كل تشغيل — فالترحيل والمخطط الجديد
لا يمكن أن ينفصلا. انظر `docs/LICENSING.md`.

## الإثبات

`tools/prove_runtime.py` (الفحص B) يبني جدول leaderboard **بصيغته القديمة فعلياً**، يزرع
صفوفاً قديمة، يطبق خطوة v3 حرفياً من `db/migrations.json`، ويتحقق من: العودة للخلف
(backfill)، رفض التكرار بالمفاتيح الجديدة، و**إعادة تشغيل الترحيل كله بلا أثر**. ثم يُعاد
تشغيله بعد حقن عيب متعمد ليُثبت أنه يفشل فعلاً عند العطب.
