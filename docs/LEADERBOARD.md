# لوحة الصدارة — الأنماط الثمانية والسلال الزمنية

> اتخذنا هنا قرارتين هندستين تحسمان الفرق بين «سكربت يُباع مرة» و«منتج يُحدَّث»:
> الترحيلات، والسلال الزمنية المحسوبة في PHP لا في SQL.

## العقد العام — أسماء مطابقة لواجهة CloudArcade

`GET /api/leaderboard?game=<slug|id>&type=<type>&amount=<1..100>`

| type | الفترة | النطاق |
|---|---|---|
| `top` | كل الأزمنة | لعبة واحدة |
| `top-day` | اليوم (UTC) | لعبة واحدة |
| `top-week` | أسبوع ISO الحالي | لعبة واحدة |
| `top-month` | الشهر الحالي | لعبة واحدة |
| `top-all` | كل الأزمنة | كل الألعاب |
| `top-all-day` | اليوم | كل الألعاب |
| `top-all-week` | الأسبوع | كل الألعاب |
| `top-all-month` | الشهر | كل الألعاب |

الاستجابة:

```json
{"ok": true, "type": "top-week", "game": "neon-worm",
 "period_key": "2026-W36", "amount": 10,
 "rows": [{"rank":1,"game_id":1,"game_slug":"neon-worm","alias":"سارة","score":700,"submitted_at":"..."}]}
```

- نوع مجهول → `422` · لعبة غير موجودة للأنماط الخاصة بلعبة → `404` · `amount` يقف عند 100.
- لوحات `top-all*` تعرض **كل لاعب مرة واحدة** بأفضل نتيجة عبر الألعاب.

## الكتابة: صف واحد لكل (لعبة، لاعب، فترة، مفتاح-فترة)

كل تسجيل نتيجة يكتب **4 صفوف** (day/week/month/all) في معاملة واحدة. الـupsert يحفظ
«الأفضل» لكل سلة: `ON CONFLICT ... DO UPDATE ... WHERE excluded.score > score` —
النتيجة الأقل المتأخرة لا تمحو الأفضل الأقدم. مثال ثبتْه `tools/prove_runtime.py`:
سارة سجّلت 500 ثم 700 ثم 600 في اليوم نفسه → لوحة اليوم تعرض 700 فقط.

**لماذا لا توجد دوال تواريخ في SQL؟** لأن مفتاح الفترة (`2026-09-05` / `2026-W36` /
`2026-09` / `all`) يُحسب في PHP من ساعة واحدة (UTC) ويُخزَّن في الصف — فتُقرأ كل لوحة
بـ`WHERE period = ? AND period_key = ?` مفهرسة فقط، و`DATE()` في MySQL مقابل
`strftime()` في SQLite لا تدخل الصورة أصلاً. راجع `src/Gamify/Buckets.php`.

## سلامة النتائج (طبقتان)

1. **رمز الصفحة** (`Gamify\Signer`): الخادم يوقّع `game|ts|nonce` بمفتاح التثبيت
   ويُضمّنه في HTML؛ `POST /api/score` يرفض أي طلب بلا رمز صالح (عمر ≤ 10 دقائق).
   سرّ HMAC لا يصل العميل أبداً.
2. **توقيع الصف**: كل صف مخزّن يحمل HMAC على محتواه، و`verifyRow()` يتحقق قبل العرض —
   العبث المباشر بالجدول يُكشف عند القراءة.

الحد الأقصى للنتيجة 99,999,999، والنتيجة ذاتها يرسلها العميل ضمن حدود الـrate-limit —
هذه هي السقف الصادق لأي أركيد يُنفَّذ في المتصفح، بما فيهم المنافسون التجاريون.

## المخطط

```
leaderboard(game_id, user_id?, alias?, score,
            period('day'|'week'|'month'|'all'),
            period_key, week_key*, signature?, submitted_at)
UNIQUE (game_id, user_id, period, period_key)   -- لاعب مسجّل
UNIQUE (game_id, alias,  period, period_key)    -- زائر (alias دائماً غير فارغ للزوار)
INDEX  (game_id, period, period_key, score)     -- لوحات اللعبة: فهرس-فقط
INDEX  (period,  period_key, score)             -- لوحات top-all*
```

`week_key` عمود توافق مع التثبيتات الأقدم من السلال v3؛ يُملأ بقيمة `period_key` حين
`period='week'` وإلا يبقى `''`.

## التشغيل والإثبات

```
$ python3 tools/prove_runtime.py     # 19 فحصاً: DDL كامل + ترحيل حقيقي + اللوحات الثمانية
$ python3 tools/verify_php.py        # 26 فحصاً بنيوياً (مثبت عدم-فراغه بحقن عيوب)
$ npm test                           # الجسر + البوابتان + تطابق اللهجتين + صحة JSON
```

تعطيل السمات الزائفة ممنوع: أي تعديل على `GAME_*` أو قواعد الفحص يجب أن يمر على
`tools/prove_runtime.py` قبل الدمج.
